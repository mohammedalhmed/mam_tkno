# خارطة التطوير

## المرحلة 0 — تثبيت المرجع

**الحالة:** منفذة في هذه المراجعة.

- اعتماد ميثاق المشروع ومصدر البيانات.
- توحيد وصف المنتج: موقع ثقة + كتالوج أنواع + b​​rief builder.
- تثبيت حدود static وواتساب وعدم وجود تسعير تلقائي.

## المرحلة 1 — تجربة الاكتشاف

**الحالة:** منفذة.

- هوية MAM_Tkno وRTL والوضعان اللونيان.
- مشاريع BellaBox وNERFONA وALTAJ PLUS.
- خدمات، أسئلة شائعة، وطرق تواصل.

## المرحلة 2 — كتالوج الأنواع وباني brief

**الحالة:** منفذة.

- ستة تصنيفات مع صفحات وإضافات وأسئلة متخصصة.
- modal حقيقي مع backdrop مموه وإغلاق Escape.
- صفحات أساسية محددة تلقائيًا وقابلة للتعديل.
- إضافات اختيارية مع كشف تدريجي.

## المرحلة 3 — الاقتراحات الذكية الخفيفة

**الحالة:** منفذة.

- اقتراح النوع من المجال.
- اقتراح الإضافات بحسب النوع.
- شارات تفسيرية وإلغاء يدوي.
- اختبارات Playwright للتاجر والحجز وعدم overflow.

## المرحلة 4 — تحسين التسليم

**الأولوية التالية:** متوسطة.

- إضافة شاشة مراجعة أكثر اختصارًا قبل واتساب.
- إظهار الفرق بين الصفحات والإضافات في ملخص قابل للنسخ.
- دعم حفظ draft محليًا بموافقة واضحة، إن كان مطلوبًا.

## المرحلة 5 — خدمة خلفية اختيارية

**لا تبدأ قبل اعتماد المتطلبات.**

- endpoint لاستقبال brief.
- لوحة داخلية لمراجعة الطلبات.
- حالة الطلب ورسائل المتابعة.
- حماية البيانات، موافقة، ومدة احتفاظ.

## المرحلة 6 — تحويلات وقياس

- قياس فتح الكتالوج وفتح modal وإكمال كل خطوة.
- قياس النقر على واتساب دون تسجيل محتوى الحقول.
- اختبار نسخ CTA والعناوين.

## بوابة كل إصدار

```bash
pnpm run check
pnpm run build
pnpm run verify:seo
pnpm run test:visual
```

ثم مراجعة 390 و768 و1280، تنظيف artifacts المؤقتة، وحفظ checkpoint وصفي.

## قواعد الأولوية

1. صحة البيانات والوضوح قبل إضافة ميزات جديدة.
2. تجربة الهاتف قبل الزخرفة البصرية.
3. الوظيفة المقترحة يجب أن تفسر سببها وتبقى قابلة للإلغاء.
4. أي backend أو تكامل خارجي يحتاج مواصفة مستقلة قبل التنفيذ.
